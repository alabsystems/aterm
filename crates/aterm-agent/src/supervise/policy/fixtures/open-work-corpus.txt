# OPEN-WORK CORPUS: what the open-work reader (`open_work` in
# supervise/policy/turn_end.rs) must make of real done reports.
#
# Excerpts of the reports this repository's own agents ended with
# ATERM-TASK-DONE in three rounds of work (2026-10-15 to 2026-10-17): each
# implementer's summary, skipped items and open risks, and each reviewer's,
# integrator's and measurer's notes. Trimmed to the excerpts that leave work
# open or hold one of the reader's words; paths outside the repository read
# <scratch>, <worktrees>, <build-cache> and <checkout>.
#
# Labels follow the owner's rule for a finished job (2026-10-19: the token
# NEVER ends a job while ANY follow-up is left). An excerpt is OPEN when it
# leaves something undone (a check not run, a gap still open, something
# unmeasured, unexplained or left to follow up), WHATEVER BLOCKS IT: one that
# names its blocker (a person's credential or decision, what this host
# lacks), a decision not to do it, or the later step it is left to, is open
# all the same. It is CLEAR when it leaves nothing: nothing undone, or a
# reason why there is nothing to do (no contract was added, main already has
# it, the brief forbids it).
#
#   === <report>                a report: its excerpts, joined, are one report
#   --- open  /  --- clear      an excerpt and its label
#   --- open, missed: <why>     the reader finds no open work in it
#   --- clear, flagged: <why>   the reader finds open work in it
#
# A report reads as open exactly when one of its excerpts does.

--- clear
What I found, checked with my own C probes before touching any code (scratchpad <scratch>/nt5/: probe.c, probe2.c, probe3.c, probe4.c, probe6.c, ctrlc.c, syms.c):
- The brief's recipe was POSIX_SPAWN_SETSID|CLOEXEC_DEFAULT|SETSIGDEF(all)|SETSIGMASK(empty), with the slave opened by addopen(0, pts, O_RDWR) and no O_NOCTTY, then dup2 0->1,2. The child does become a session leader (getsid==pid), but it has no controlling terminal. tcgetsid(master) fails with ENOTTY and tcgetpgrp(master) is 0, checked at 0, 50 and 500 ms after the spawn.
- An interactive zsh started that way: Ctrl-C did not stop `sleep 30` in 3 of 3 runs. The same zsh started by fork + login_tty: tcgetsid and tcgetpgrp both answer its pid, and Ctrl-C works in 3 of 3.
- python3 and /bin/sleep never get a terminal. /bin/sh (bash) gets one only because bash opens its own tty and takes it. That is why the auditor's check (`/bin/sh -c 'exec 3</dev/tty'`, CTTY_OK) passed: it was a false positive.
- The parent is not affected: a session-leader parent with no controlling terminal (the Finder shape) still gets ENXIO from /dev/tty in every variant (with or without SETSID, with or without O_NOCTTY).
- dlsym finds no libSystem posix_spawn hook that could set a controlling terminal (no addtcsetpgrp, addctty or setsessionid).
- Side facts for anyone who tries again: the parent must keep its slave open across the spawn, or termios and winsize reset to 9600 and 0x0 when the child opens the slave. A failing addchdir_np fails the whole spawn (ENOENT), where the fork path's failed chdir is not fatal.

## Regression: a 3–5 ms main-thread block on a fresh install's first launch
- **What happens:** round 3 has a 2.68–4.76 ms `user_event` turn on a fresh root, about 14–18 ms after start. It shows in 7/8, 9/10 and 10/10 idle-launcher runs and in 4/12 equalized ones. Round 2 has none (0.33–0.40 ms), and warm launches have none.
- **Cause, proven by A/B on the round-3 binary:**
  - On a fresh root, the document journal's open thread (`aterm-journal-open`) mints its key with `sync_all`, which is `F_FULLFSYNC` on macOS. `crates/aterm-gui/src/durable.rs` itself says this stalls the whole volume.
  - Round 3's main thread writes log lines (the new AI "not installed" entries from 1b2685414d) inside that window. Every synchronous write it makes then waits until the flush finishes.
  - Round 2 minted the same key but wrote nothing on the main thread in that window.
- **Evidence:**
  - `[ai] enabled = false`: 0.36–0.47 ms (8/8 runs).
  - Journal key copied in beforehand, so nothing is minted: 0.35–0.47 ms (10/10).
  - Default: 3.06–4.76 ms.
  - A temporary probe build (never committed, reverted) showed the blocked wake using 46–102 µs of thread CPU over 3.5–4.6 ms of wall time. A 1 ms sample caught the main thread inside `write(2)`, with `aterm-journal-open` in `sync_all` at the same moment.
- **Impact:** once per install, before session0's prompt. The cold prompt is still 3 ms faster than round 2. The underlying hazard is wider: any synchronous `aterm.log` write on the main thread waits out any `F_FULLFSYNC` on the volume, whether aterm's own or another process's.
- **Not fixed here:** this step is measurement only. The fix is a change to the logger design: main-thread log writes going through a writer thread, the pattern `messages_store` already uses. This needs to be scheduled as its own piece of work.
